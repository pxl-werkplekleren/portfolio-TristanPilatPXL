01. Beschrijving van de case

De opdrachtgever

Pop & Clay is een lokaal bedrijf dat workshops en handgemaakte producten rond kleiboetseren aanbiedt. Vóór ons project beheerde de eigenaresse haar volledige digitale aanwezigheid uitsluitend via Instagram: geen eigen website, geen centrale productcatalogus, geen klantportaal en geen systeem om bestellingen of gebruikers bij te houden. Dat werkte aanvankelijk, maar naarmate het bedrijf groeide werd het beheer te omslachtig en onprofessioneel voor een groeiend klantenbestand.

De opdracht

Wij kregen de opdracht om een volwaardige webapplicatie te bouwen die drie gebruikerstypes ondersteunt: klanten die het productaanbod kunnen bekijken, medewerkers die producten en bestellingen beheren via een beveiligd portaal, en een administrator die het volledige platform beheert, inclusief gebruikersbeheer, medewerkersbeheer, een loginlogboek en systeeminstellingen. Elke gebruikersrol heeft eigen schermen, eigen rechten en een eigen toegangsniveau.

De technologiestack

Het project was opgesplitst in afzonderlijke onderdelen. De publieke klantfacing website werd verzorgd door de webstudent in het team. De programmeurs concentreerden zich op het admin dashboard, de backend API en de database.

Het admin dashboard is gebouwd in HTML, CSS en vanilla JavaScript. Er is geen frontend-framework gebruikt: alle interactie, formuliervalidatie, routing tussen schermen en API-communicatie verlopen via zelfgeschreven JavaScript met de Fetch API en session storage voor tokenbeheer. De interface bevat schermen voor gebruikersbeheer, medewerkersbeheer, productbeheer, bestellingenbeheer, een loginlogboek en profielbeheer.

De backend is een ASP.NET Core Web API, geschreven in C# op .NET 8. Authenticatie verloopt via JWT-tokens en wachtwoorden worden opgeslagen als bcrypt-hashes. Toegangscontrole is role-based: admin, medewerker en gebruiker hebben elk andere rechten op de endpoints. De API documenteert zichzelf via Swagger/OpenAPI. Intern is de backend gestructureerd met het repository pattern en dependency injection. De database draait op SQL Server en bevat tabellen voor gebruikers, medewerkers, producten, bestellingen, adressen, reviews en loginlogs.

Het team

We werkten met acht studenten uit drie richtingen: vier programmeurs, één webstudent en drie studenten digitale vormgeving. De vormgevers zorgden voor het visuele ontwerp, de UX-wireframes en de huisstijl op basis van de briefing van de opdrachtgever. De webstudent bouwde de publieke klantfacing frontend. De vier programmeurs, waaronder ik, waren verantwoordelijk voor de backend-logica, de database-architectuur, de REST API en het admin dashboard.

02. Mijn aandeel

Mijn rol

Binnen het team van acht waren vier programmeurs verantwoordelijk voor de backend, de database en het admin dashboard. Mijn aandeel lag over de volle breedte van die stack.

Frontend: HTML, CSS en JavaScript

Aan de frontendzijde van het admin dashboard werkte ik aan schermen voor bestellingenbeheer en gebruikersbeheer. Dat omvatte het opbouwen van overzichtsschermen met dynamisch geladen data via de Fetch API, formulieren voor het aanmaken en bewerken van records, client-side invoervalidatie en foutafhandeling bij API-responses. De authenticatieflow aan de frontendzijde, inclusief het opslaan van het JWT-token in session storage, het uitlezen van de gebruikersrol en het doorsturen naar het juiste scherm, was een onderdeel waar ik aan werkte en waarbij ik ook foutopsporing deed tussen de JavaScript-code en de backend.

Backend: C# ASP.NET Core

Aan de backendzijde werkte ik mee aan de API-endpoints voor de modules waaraan ik bijdroeg, inclusief de opzet van controller-klassen, de repository-implementaties en de koppeling met de database. Ik paste het repository pattern toe zoals dat in het project was afgesproken en werkte met dependency injection voor de koppeling van services.

Database: SQL Server

Voor de database droeg ik bij aan het opzetten van een deel van het schema en het schrijven van de bijhorende queries. Ik testte de koppeling via Swagger voor de frontend erop werd aangesloten. Dat testen was nuttig: het maakte duidelijk welke endpoints correct functioneerden en welke nog bijgestuurd moesten worden, voor het eigenlijke integratiewerk begon.

Samenwerking en afstemming

Buiten het technische werk leerde ik in dit project dat afstemming minstens zo belangrijk is als code schrijven. Vroeg in het project stelde ik mee voor om gezamenlijk de datamodellen en de structuur van de API-endpoints vast te leggen. Die afspraak heeft later integratieproblemen vermeden. Ik leerde ook dat het bewaken van een gedeelde structuur, consequente naamgevingsconventies en afgesproken respons-formaten, in een teamproject een groter effect heeft dan ik in een solo-project ooit had kunnen ervaren.

03. Wat ik leerde

🤝 Full-stack teamwerk

In een team van acht met drie disciplines leer je dat goede afspraken over API-contracts en component-grenzen essentieel zijn. We definieerden vroeg in het project samen de datamodellen en API-endpoints, wat later refactoring-werk voorkwam. Ik leerde ook communiceren met design-studenten over technische haalbaarheid van hun mockups.

Vanilla JavaScript in een echte applicatie

Het bouwen van een volledig admin dashboard zonder framework dwingt je om alles bewust te structureren. Ik leerde de Fetch API correct te gebruiken voor beveiligde requests met een Authorization-header, API-responses netjes te verwerken inclusief foutstatussen, en de gebruikersinterface te updaten zonder een framework dat dat voor je doet. Dat geeft inzicht in wat frameworks eigenlijk oplossen.

SQL Server en repository pattern

Door de databaselogica volledig te scheiden van de controller via het repository pattern, blijft elke laag leesbaar en aanpasbaar zonder de rest te breken. Ik leerde hoe een goed ontworpen databaseschema met duidelijke relaties tussen tabellen de backend eenvoudiger maakt, en hoe een kleine fout in een tabelstructuur of kolomnaam uren debuggen kan kosten.

🔄 Wat ik anders zou doen

Ik zou vroeger pleiten voor een gezamenlijke backlog of taakbord. In de beginfase waren taken niet scherp genoeg verdeeld, wat leidde tot korte overlappingen tussen programmeurs. Een gedeelde sprint-planning aan het begin van elke week had dat eenvoudig voorkomen en ons tempo verhoogd.

04. Finaal resultaat

🚀 Het eindproduct

Het eindresultaat is een volledige webapplicatie voor Pop & Clay met drie afzonderlijke gebruikersomgevingen. Klanten kunnen het productaanbod bekijken, medewerkers en admins beheren het platform via een admin dashboard gebouwd in HTML, CSS en vanilla JavaScript. De backend is een ASP.NET Core Web API in C# met JWT-authenticatie, bcrypt en role-based access control. De database draait op SQL Server.
